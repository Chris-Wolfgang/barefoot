# What barefoot can take from WMS — review of `Chris-Wolfgang/wms` (2026-11-06)

Read on `wms` `origin/main` @ 369aeeb: README, `docs/*.md`, `docs/adr/0001–0005`, docfx operator pages,
`tests/Wolfgang.Wms.UnitTests/Architecture/*`, `.claude/skills/*`, the Migrate tool and the HTTP helpers in
`Wolfgang.Wms.Core/Http`. WMS is a modular monolith (API + Blazor consoles + Android, SQL Server + PostgreSQL,
local accounts, device sync); barefoot is a one-API / Blazor Web App / Azure SQL serverless / Entra product.
The two differ where their constraints differ; the reusable parts are the engineering conventions.

## B. Where WMS chose differently — and whether to reconsider

| WMS | barefoot | Verdict |
|---|---|---|
| Sequence-backed global `bigint row_version` + update trigger: concurrency token, ETag, delta watermark and cache stamp in one (`DATABASE-CONVENTIONS.md` "Row versioning (E5.1)", ADR 0003) | Per-row portable `Version` (SQLite tests) | **Keep `Version`.** WMS's reason is device delta sync, which barefoot lacks. Cost: no free collection ETags (`EntityTag.FromCollection` = max version + count) or `VersionedCache` invalidation — use `max(UpdatedAt)`+count or a per-table generation counter if needed. Bonus: no `HasTrigger` / `OUTPUT` clause problem. |
| `long` identity keys, no GUID columns, clients never generate ids | Guid keys, Entra `oid` as user key, `Guid.Empty` sentinel | **Keep Guids**; consider sequential Guids (`SequentialGuidValueGenerator`) for clustered-index locality on Azure SQL. |
| SQL Server + PostgreSQL, per-provider migration assemblies | Azure SQL + SQLite tests | No change. Take only the "convention verifier runs on every provider" idea and add the SQL-container/`--script` CI step above. |
| API refuses to start when DB unreachable/behind | Readiness states | **barefoot is right**; see A.2. |
| Local accounts + API-issued cookie, PBKDF2, bootstrap admin | Entra B2B, JWT | No change. Keep the cookie-on-Web / token-server-side shape. |
| Modular monolith, `ModuleDescriptor`, vertical slices | Data + Business layers behind one API | Layers suffice at barefoot's size; adopt the ADR 0001/0002/0003 points listed above. |
| Integrity HMACs on security rows, DP key ring, `enc:v1:` connection strings | Managed identity, Key Vault | Skip (threat model is on-prem rogue DBA). Keep an `ISecretProtector` only if an e-mail provider key is stored in settings; Key Vault references are simpler. |
| Native AOT + trim analyzers everywhere | Not required | Skip; this also weakens ADR 0004's case for Kiota over NSwag. |
| Kiota-generated client committed under `Generated/`, regenerated in the same PR; hand-written `Create(HttpClient, IAuthenticationProvider?)` entry point; `ClientIsolationTests` | `ApiClient` implements Core interfaces over HTTP | **Open question.** Spec-driven generation + thin hand-written adapters `XxxApiClient : ICoreInterface` keeps both properties. Decide in a barefoot ADR (0010?) before the ApiClient phase; WMS ADR 0004's rejection of NSwag/Refit is reusable reasoning. |
| Strict keyset paging, no page numbers | "Showing 1–25 of 62" + Prev/Next in the mockup | Compatible; see A.11. |

## C. Document shapes to mirror

- **ADR**: `# ADR NNNN: <decision as a choice>` · `**Status:** Accepted (<story>) · **Date:**` · `## Context` · `## Decision` (numbered, bold lead-ins, a "Not chosen:" bullet) · `## Consequences`; dated in-place amendments. barefoot's 0001–0009 already follow this loosely; add the "Not chosen" bullet and amendment convention.
- **Conventions docs** pair every rule with *how it is enforced*, tag sections with the story ID, and state "X.md is the contract; in code: …".
- **Engineering doc ↔ operator doc twins**: `docs/MIGRATE.md` ↔ `docfx_project/docs/migrate.md`, `docs/AUTH.md` ↔ `sign-in.md`, each saying "keep the two in step". The docfx pages are short, task-oriented, table-heavy; `device-app-version.md` "What the server answers" (Situation | Status | Error code + JSON) is the template for barefoot's **readiness states** page; `integrity.md` ("Guarded against / Not guarded against / Verification / Repair / Upgrade") is the template for a security page.
- **`docs/BOOTSTRAP.md`** "exceptions to the one-API rule" table (Step | Why outside the API | Runs as | Defined by) — barefoot's rows: `bf-maint migrate`, Entra app registration, managed-identity DB user grant, `bf send-digests` if it bypasses the API.
- **README "Features" table**: Area | On `main` today | Arrives with — honest status that never overclaims.
